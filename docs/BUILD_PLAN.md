# Build Plan — splitting ScreenMaster into microservices

> The roadmap. Derived from the field guide's lab ([microservices-interview-field-guide.md §10](microservices-interview-field-guide.md)) and the proposed decomposition ([ARCHITECTURE_AND_SCHEMA.md §8](ARCHITECTURE_AND_SCHEMA.md)). Each step states **goal · what we build · the concept it teaches · "done when"**. Concept links point at [docs/concepts/](concepts/).
>
> **Principle:** build it properly, then *feel* each microservices cost and be able to narrate it. Production-grade by default (validation, idempotency, error handling, tests) — see [CLAUDE.md](../CLAUDE.md). Don't gold-plate scope; do gold-plate correctness on the paths that move money or hold seats.

## The shape we're building toward

```
browsers / curl ─▶ GATEWAY ─┬─▶ CATALOG      (movies, genres, TMDB)        catalog-db
                            ├─▶ BOOKING      (showtimes, seats, bookings)  booking-db   ← core
                            ├─▶ PAYMENT      (Stripe + Paymob + sandbox,   payment-db
                            │                 sessions, webhooks, refunds)
                            ├─▶ NOTIFICATION (consumes BookingConfirmed)   (no db / dedupe table)
                            └─▶ IDENTITY     (Keycloak)                     keycloak-db

        Stripe / Paymob ──webhook──▶ PAYMENT ──PaymentSucceeded──▶ BOOKING ──▶ CONFIRMED
        (the ONLY path to PAID — the browser never confirms a payment)

        all services register with ─▶ EUREKA        async events over ─▶ RABBITMQ
        traces ship to ─▶ ZIPKIN
```

Five business services + gateway + Eureka, on Docker Compose, with **database-per-service**. (We collapse the schema doc's Theater + Scheduling into Booking, since the booking transaction only needs *immutable facts* from them — see [service-decomposition-ddd.md](concepts/service-decomposition-ddd.md).)

## Phase 3 — The booking saga (orchestrated, async payment)  *(field guide M3)*
**Goal:** re-earn the cross-service transaction with a saga + compensation — against **real payment gateways**, where the answer arrives out-of-band by webhook and no database transaction can span the charge.

> **Plan:** [plans/real-payment-gateway/plan.mdx](../plans/real-payment-gateway/plan.mdx). **Concept:** [payment-gateway-integration.md](concepts/payment-gateway-integration.md).
>
> **The shape.** Booking owns the booking and its seats; Payment owns payments, attempts, gateway sessions, webhooks, and refunds. **Payment never writes booking-db, and Booking never calls Payment.** The client asks Payment for a checkout session; the gateway's verified webhook is the only thing that writes `PAID`; Payment then publishes `PaymentSucceeded` over the existing `screenmaster-exchange`, and Booking decides whether to confirm.
>
> ```
> POST /bookings ──▶ Booking: PENDING, seats held, expiresAt = +15 min
> POST /payments ──▶ Payment: Payment(PENDING) + PaymentAttempt(PENDING) ──▶ gateway session ──▶ checkout URL
> user pays ──▶ gateway ──webhook (signed)──▶ Payment: attempt SUCCEEDED, payment PAID, outbox row
>                                             ──▶ relay ──▶ PaymentSucceeded ──▶ Booking
> Booking: confirm IF still PENDING and now < expiresAt, else BookingConfirmationRejected ──▶ auto-refund
> ```
>
> **Two clocks, deliberately separate:** the *booking hold* (15 min) and the *gateway session* (shorter, gateway-set). A lapsed session is recoverable — "Pay Again" opens a new attempt on the **same** Payment. A lapsed booking is not: the seats may already be resold, so the user must book again.

- [x] **3.0 Payment domain rebuild — real gateways behind one port.** Replace the fake provider with the real model. **Schema** (Liquibase, `ddl-auto=validate`, all enums STRING): `payments` (booking_id **UNIQUE** — one obligation per booking; amount + **currency**; `refunded_amount`), `payment_attempts` (gateway, session/payment ids, `checkout_url`, `expires_at`, idempotency key, + a **partial unique index on `(payment_id) WHERE status='PENDING'`** so two concurrent "Pay" clicks cannot open two sessions), `refunds`, `webhook_events`. The 1.2 `payments` table is **dropped and recreated** — it has no `booking_id` and no rows worth keeping (safe because payment-db is Payment's alone). **Port + registry:** a `PaymentGateway` interface (`type()`, `supportedCurrencies()`, `createSession()`, `fetchStatus()`, `refund()`, `parseAndVerifyWebhook()`) with a `GatewayRegistry` built from `List<PaymentGateway>` — **no gateway-specific `if/else` anywhere outside an adapter**. - [x] **3.1 Booking core + the payability read.** `POST /api/bookings` already creates `PENDING` with the local double-booking guard (built early in 2.2) — keep it. Add the bounded **`GET /bookings/{id}/payability`** returning `{status, expiresAt, userId, totalAmount, currency}`, the single read Payment needs for guards 1–4 (mirrors how Booking already calls Catalog in 2.1c/2.2). - [ ] **3.2 Webhooks — the only path to PAID — + payload storage, idempotency, and the outbox.** A per-gateway endpoint (`POST /payments/webhooks/{stripe,paymob,sandbox}`) reading the **raw body bytes** (signatures are computed over exact bytes — a Jackson round-trip breaks verification). Then: **verify the signature** (constant-time `MessageDigest.isEqual`; bad → 400, stored, alerted, dropped) → **store the event** (raw payload + headers + signature outcome + gateway event id) in `webhook_events` **before any business logic**, in a `REQUIRES_NEW` transaction so the evidence survives a rolled-back business transaction → the `UNIQUE (gateway, event_id)` violation **is** the dedupe (duplicate → 200, do nothing) → find the attempt → **normalize** the gateway's vocabulary (`success`, `checkout.session.completed`) into our enum → update attempt + payment → write `PaymentSucceeded`/`PaymentFailed` to an **outbox** row *in the same transaction*, drained by a `@Scheduled` relay (`FOR UPDATE SKIP LOCKED`). **Answer 200 to almost everything** — unknown session, already-processed, uninteresting event type — because a gateway retries any non-2xx for hours. *(Concepts: [transactional-outbox.md](concepts/transactional-outbox.md), [idempotent-consumer.md](concepts/idempotent-consumer.md), [rabbitmq.md](concepts/rabbitmq.md), [security-jwt-oauth2.md](concepts/security-jwt-oauth2.md))*
  > **Why the outbox moves here from Phase 4:** 2.3 accepted a direct `AFTER_COMMIT` publish because a lost `MovieUpserted` self-heals via lazy backfill. A lost `PaymentSucceeded` does not — the money is gone and the booking never confirms. Phase 4 then *generalizes* this mechanism to Booking rather than introducing it.
  > **Local delivery:** gateways cannot reach `localhost`. Stripe uses `stripe listen --forward-to localhost:8083/payments/webhooks/stripe`; Paymob uses an **ngrok** tunnel whose URL goes in the Paymob dashboard. Both are read from `PAYMENT_PUBLIC_URL`, never hardcoded.
- [ ] **3.3 Booking confirms from the event.** Booking binds its own queue to `screenmaster-exchange` and consumes `PaymentSucceeded`. The confirm is **one conditional UPDATE**, not read-then-write: `set CONFIRMED where id = ? and status = PENDING and expiresAt > now()`. **1 row → confirmed** (emit `BookingConfirmed` for Notification). **0 rows → re-read to tell apart** "already CONFIRMED" (a redelivered event — idempotent no-op) from "EXPIRED/CANCELLED" (publish `BookingConfirmationRejected`). `PaymentFailed` only mirrors `paymentStatus`; seats stay held so the user can retry until the hold lapses. `Booking.paymentStatus` survives but is **demoted to a read-model mirror** — Payment is the source of truth, and the field is displayed, never used to decide. *(Concepts: [saga-pattern.md](concepts/saga-pattern.md), [idempotent-consumer.md](concepts/idempotent-consumer.md), [cqrs-read-model.md](concepts/cqrs-read-model.md))*
- [ ] **3.4 Two expiry sweepers, one per clock.** In **Booking**: the `@Scheduled` job that expires stale `PENDING` bookings past `expiresAt` and frees seats — the saga timeout, and a flagged monolith gap. In **Payment**: a job that marks lapsed `PENDING` attempts `EXPIRED`. They are independent: at 20:06 a dead session with a live booking → "Pay Again" works; at 20:16 the booking is gone → no new attempt, book again. *(Concept: [saga-pattern.md](concepts/saga-pattern.md) — timeout as compensation trigger)*
- [ ] **3.5 Refunds + the expiry-race compensation.** `refunds` is a child table, not a status flip, because partial refunds are real (1000 EGP refunded 300 then 200 leaves 500 refundable). The invariant `Σ refunds ≤ payment.amount` is checked **under a row lock**; a refund is `SUCCEEDED` only when its own gateway webhook says so, and `payment.status` becomes `REFUNDED` or `PARTIALLY_REFUNDED` from the running total. Two entry points: **automatic** (consume `BookingConfirmationRejected` → full refund, no human) and **admin** (`POST /payments/{id}/refunds`, ADMIN-only from Phase 7, gateway-unrouted before then). **Decided:** paid-after-expiry → **auto-refund, no seat recovery** — deterministic, needs no operator, and it makes the refund path load-bearing so the ordinary demo exercises it. *(Concept: [saga-pattern.md](concepts/saga-pattern.md) — compensating action, not rollback)*
- [ ] **3.6 Reconciliation — webhooks are not the only recovery.** A `@Scheduled` sweep every 5 min: for attempts `PENDING` longer than 10 min, call `fetchStatus()` and apply the result **through the same handler the webhook uses** (dedupe insert included, keyed `recon:{attemptId}:{status}`), so a late webhook is a no-op. Attempts past `expires_at` with no gateway record → `EXPIRED`. Same shape as catalog's resumable sync. This is what makes the webhook path *recoverable* rather than *critical* — without it, the first missed delivery needs a manual DB edit. *(Concept: [scheduled-resumable-sync.md](concepts/scheduled-resumable-sync.md))*
- [ ] **3.7 Break it on purpose.** Against `SANDBOX` at a 30% failure rate, fire 50 bookings and assert: **zero orphaned seat holds**, **zero double-charges**, **zero double-confirms**. Then the adversarial cases: deliver the same webhook 5× (one PAID, one stored event, five 200s) · deliver `PaymentFailed` *after* `PaymentSucceeded` (out-of-order — the terminal-state guard drops it) · forge a webhook with a bad signature (400, stored with `signature_valid=false`) · force paid-after-expiry via clock skew (auto-refund, visible in the Stripe dashboard) · stop Payment, pay in the gateway, restart (reconciliation finds it).

**Done when:** the 50-booking script leaves no leaked seats and no double-charges under 30% payment failure; a webhook replayed 5× confirms exactly once; a payment landing after booking expiry is automatically refunded; and a payment made while Payment was down is recovered by reconciliation.
**Talk track:** *"My saga survives a 30% failure rate with zero leaked seat holds and zero double-charges — the gateway's signed webhook is the only thing that can mark a payment paid, it's idempotent by the gateway's own event id, and anything the webhook misses gets reconciled. I can't wrap a gateway call in a transaction, so I use idempotency, state transitions, and compensating refunds instead."*

## Phase 5 — Break the gateway, watch resilience  *(field guide M5)*
**Goal:** make the system survive a **payment gateway** being slow or down — the genuinely untrusted dependency.

> **Changed by Phase 3:** Booking no longer calls Payment, so there is no Booking→Payment client to wrap. The breaker moves onto **Payment's outbound gateway calls**, which is what circuit breakers are actually for: an external third party you neither own nor can restart. The lesson is unchanged and the demo gets more honest.

- [ ] **5.1 Resilience4j on Payment's gateway clients:** per-gateway timeout (2 s), 3 retries with backoff+jitter **on `createSession` only when it is safe** (the gateway idempotency key makes a retry non-duplicating), circuit breaker + **bulkhead per gateway** so a hanging Paymob cannot exhaust the threads Stripe needs. Fallback for `createSession` = coded `503 PAYMENT_GATEWAY_UNAVAILABLE` with the attempt row **left PENDING** for reconciliation to resolve — never a silent success, never a lost attempt. *(Concept: [resilience-patterns.md](concepts/resilience-patterns.md))*
- [ ] **5.2 Observe:** point `SANDBOX` at a dialed-up latency/failure rate during a load loop → timeouts → breaker opens (`/actuator/circuitbreakers`) → fast-fail into the coded 503 → restore the gateway → half-open → recover → the reconciliation job resolves every attempt stranded during the outage. Show that the other gateway kept serving throughout (bulkhead).

**Done when:** you can narrate the breaker opening and recovering with numbers from `/actuator`, **and** show that no attempt stranded by the outage was left unresolved.
**Talk track:** the [resilience interview answer](concepts/resilience-patterns.md), past tense, with numbers — plus *"the retry is only safe because the gateway idempotency key makes it non-duplicating."*

## Phase 7 — Lock the doors with Keycloak  *(field guide M7)*
**Goal:** edge auth + zero trust between services. (Doubles as Spring Security / Keycloak study.)

- [ ] **7.1 Keycloak container:** realm `cinema`, a public client for users, a `booking-service` client with client-credentials. *(Concept: [security-jwt-oauth2.md](concepts/security-jwt-oauth2.md))*
- [ ] **7.2 Resource servers:** gateway + every service validate the JWT (issuer-uri). RS256, not the monolith's shared HMAC secret.
- [ ] **7.3 Service-to-service:** Booking no longer calls Payment (Phase 3), so there is no token to relay there — instead: **Payment→Booking** (`GET /bookings/{id}/payability`) carries the relayed user token; the outbox relay uses its own client-credentials token (never put a user JWT in a queue message — the event carries the user id and the consumer acts with a machine token). **Webhook endpoints are the deliberate exception:** a payment gateway has no JWT, so `/payments/webhooks/**` is permitted at the security layer and authenticated by **signature verification** instead — a different mechanism proving the same thing. ## Scope guard (from the field guide)
Cut ruthlessly: **no Kubernetes** (Compose is enough), **no gRPC implementation** (the `.proto` + comparison table in [sync-vs-async-comms.md](concepts/sync-vs-async-comms.md) is enough), **no UI** (curl + the RabbitMQ console + Zipkin).

**Reversed (was "no real Stripe/PayPal"):** payments now integrate **two real gateways in sandbox mode** — Stripe (test) and Paymob (sandbox) — plus a controllable `SandboxGateway` adapter that keeps the dial-a-failure ability the resilience demos need. The original reasoning was half right: you *do* learn more from failures you control, which is why the sandbox adapter survives. But the fake provider hid the two hardest lessons in payments — **the answer arrives later, out-of-band** and **you cannot put a gateway call inside a database transaction** — and those are exactly the microservices lessons this repo exists to teach. **Sandbox credentials only:** a startup assertion rejects a live Stripe key unless `spring.profiles.active=production`, so this repo is structurally incapable of moving real money.

**If time is short, protect this order:** Phase 1 → Phase 3 → Phase 4 → Phase 5. Saga, outbox, and breaker are the three demos that change how the interview answers *sound*.
