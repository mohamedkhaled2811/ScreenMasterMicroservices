Build plan: 0.3 (Phase 0) Milestone: pre-M1 Services: gateway · discovery · catalog · booking · payment · notification

1. Summary

Convert the current single-module pom.xml into a parent (aggregator) POM and create six empty child modules: gateway, discovery, catalog, booking, payment, notification. No business logic and no @SpringBootApplication classes yet — that's Phase 1. This step exists so that from here on, each service is its own buildable unit with its own dependency surface, which is the structural precondition for everything the lab teaches: independent deployability, database-per-service, and clean boundaries. It teaches the Maven reactor (parent aggregates + manages versions; children declare only what they use).

4. Options

Decisions confirmed up front are marked. Alternatives kept so the trade-offs stay reviewable.

4a. Where dependencies live

Chosen

A — Lean parent + dependencyManagement

Parent declares versions only (Spring Cloud BOM import + Lombok etc. in <dependencyManagement>). Each child pulls just the starters it needs.

  • Gateway pulls gateway-server, not JPA; payment stays tiny — real service boundaries.
  • Versions pinned in one place; children list deps without versions.
  • Matches production multi-module layout — what an interviewer expects.
  • A little more per-child boilerplate (each lists its own starters).

Best when: services genuinely differ in what they need (they do).

B — Parent declares all common deps

Every child inherits JPA + security + web + … from the parent's <dependencies>.

  • Less boilerplate to start.
  • Couples services: discovery/payment drag in JPA they never use.
  • Hides each service's real surface area — the opposite of the lesson.

Best when: all modules are near-identical (not our case).

4b. The existing root src/

Chosen

A — Delete it

Parent POM (packaging=pom) compiles no code. Remove the placeholder app, test, and application.properties.

  • Parent stays a pure aggregator — no stray @SpringBootApplication at the root.
  • Each service gets its own bootstrap class in Phase 1, named for the service.
  • Throws away the generated starter class (it's a 3-line placeholder — no loss).

B — Move it into a child (e.g. catalog)

Relocate the placeholder app into one module as a seed.

  • Keeps a compiling Boot app immediately.
  • Misnamed throwaway class we'd rewrite in Phase 1 anyway.
  • Picks a favorite child arbitrarily.

5. Risks / microservices cost felt

This step itself surfaces no distributed-systems cost — it's the scaffold those costs will later live in. The thing it makes tangible is independent deployability: once each service is its own module/jar, you can build and run one without the others (./mvnw -pl payment package), which is exactly what lets us later docker stop payment and watch Booking's circuit breaker open (Phase 5). The production-grade choice here is the lean parent: it forces each service to declare its own dependencies, so the boundaries are real from day one rather than a shared "god classpath" we'd have to untangle later.
