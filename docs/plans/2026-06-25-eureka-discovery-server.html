Plan: Eureka discovery server (discovery)

Date: 2026-06-25 Author: Claude Code + Mohamed Status: APPROVED — A1 + B1 + C1 + concept-doc note
Milestone: M1 (skeleton) Service: discovery BUILD_PLAN 1.1 Concept: service-discovery.md

1. Summary

Turn the empty discovery module into a runnable Netflix Eureka server — the registry every other service will register with and the gateway will use to resolve lb://catalog, lb://booking, etc. Concretely: add a @SpringBootApplication + @EnableEurekaServer main class, an application.yml that pins it to port 8761 and tells it not to register with or fetch from itself, and wire the spring-boot-maven-plugin so it repackages into a runnable jar.

This is the first running service of the lab. It teaches the client-side discovery model (see concepts/service-discovery.md): services announce themselves to a registry; callers fetch the list and load-balance. Nothing registers yet — that lands in 1.2 — so the "done when" here is simply: the server boots and its dashboard answers on 8761 with an empty registry.

4. Options

The shape of the server is fixed by the milestone; the genuine decisions are three small config/quality choices. I've grouped them so you can pick per-axis.

Axis 1 — Self-preservation mode (the one that bites in dev)

Recommended

A1 — Disable self-preservation

eureka.server.enable-self-preservation: false.

  • Dead instances get evicted promptly — the dashboard reflects reality when you docker stop a service (which we do on purpose in Phases 3 & 5).
  • No confusing "EMERGENCY! Eureka may be incorrectly claiming instances are up" red banner during a tiny local lab.
  • In production this is the wrong default — self-preservation exists to survive network partitions. We'll note that in the concept doc so the trade-off is learned, not hidden.

Best when: local Compose lab where we kill services deliberately.

A2 — Leave self-preservation on (Eureka default)

Don't touch the flag.

  • Matches production defaults; nothing "non-standard" in the config.
  • Stopped instances linger in the registry for minutes; the resilience demos (Phase 5) get muddier to observe.
  • The red emergency banner appears with so few instances and confuses a first read.

Best when: you want prod-identical behavior over demo clarity.

Axis 2 — Config layout for "now localhost, later Compose DNS"

Recommended

B1 — Single application.yml, Compose overrides via env later

One plain application.yml now. In 1.4, Compose injects EUREKA_* / defaultZone via environment variables (Spring relaxed binding), no file edits needed.

  • Simplest thing that's still correct; 12-factor (config from env).
  • No profile machinery before we need it.
  • The Compose wiring isn't visible in-repo until 1.4.

Best when: you want the smallest honest step now.

B2 — Add a docker profile now (application-docker.yml)

Author both the localhost and the Compose-DNS config up front.

  • Compose behavior is explicit and version-controlled today.
  • Writes config for infrastructure that doesn't exist yet (the Compose file is 1.4) — easy to get the defaultZone hostname wrong and not notice.
  • More surface to review before it can even be exercised.

Best when: you'd rather front-load all the config.

Axis 3 — Test / verification level

Recommended

C1 — Context-load smoke test + manual curl

Keep the generated @SpringBootTest context-load test (it already pulls spring-boot-starter-test), plus we boot it once and curl 8761.

  • Catches the most common failure (mis-wired context / bad config) in the reactor build — cheap insurance, matches "production-grade by default."
  • Manual curl proves the dashboard + the Eureka REST API actually answer.
  • The context test needs a free port; we set server.port=0 in the test to avoid clashing with a running 8761.

Best when: you want a real "done when" without over-testing infra.

C2 — Manual verification only (no test)

Delete the test stub; rely on booting + curl.

  • Zero test code for a config-only module.
  • The reactor build no longer fails if someone breaks discovery's wiring; regressions surface only at runtime.

Best when: you treat discovery as throwaway infra (we don't — it's load-bearing).

5. Risks / microservices cost felt

This step doesn't yet hurt — but it introduces the machinery for the first real distributed-systems cost: instances come and go, so addresses can't be hardcoded. The registry is what later lets us docker stop payment and watch the gateway stop routing to it (Phase 5). The one trap to get right now is the self-preservation flag (Axis 1): leave it on and the registry will lie about dead instances during exactly the failure demos this whole lab is built around. We disable it for the lab and document why it exists so the production trade-off is learned, not skipped.
