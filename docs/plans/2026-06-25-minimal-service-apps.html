Plan: Minimal service apps — catalog, booking, payment, notification

Date: 2026-06-25 Author: Claude Code + Mohamed Status: APPROVED — implemented & verified (full reactor build green)
Milestone: M1 BUILD_PLAN: 1.2 Services: catalog · booking · payment · notification Schema §: 8 (decomposition)

1. Summary

Turn the four scaffolded modules into runnable Spring Boot apps. Each one boots, registers with the Eureka server (the standalone discovery service on 8761), and exposes a health endpoint at /actuator/health. catalog, booking, and payment each own a real Postgres database (managed by Liquibase). payment ships a working fake provider (POST /payments, ~300 ms latency, FAIL_RATE env var) behind a PaymentProvider interface so a real provider is an add-only swap later; it persists every charge and is idempotent (a repeated Idempotency-Key replays the original result, no double-charge). notification is a future event consumer that gets a minimal health surface now. This is the "every service is up and discoverable" slice of milestone M1 — it teaches service discovery, externalized config, actuator health, database-per-service, and request idempotency. Gateway routing (1.3) and the full Compose file (1.4) come next.

4. Options — decisions chosen with Mohamed

These forks were resolved before writing the plan. The chosen path is marked; the alternative is kept so the reasoning is reviewable.

4a. catalog/booking database in 1.2

Chosen

Real Postgres now + Liquibase

Stand up catalog and booking Postgres DBs (user creates them manually); empty Liquibase master changelog; ddl-auto: validate.

  • Matches the database-per-service + Liquibase conventions from day one.
  • Liquibase is wired and proven before any real table exists.
  • catalog/booking won't boot unless their Postgres DB is up.

Best when: you want the real shape early and don't mind a running Postgres.

Exclude DataSource autoconfig (shim)

Two yml lines exclude JPA/datasource so catalog/booking boot with no DB; real datasource lands in 2.1/3.x.

  • No Postgres needed in 1.2.
  • Temporary config to delete later.
  • Defers the database-per-service lesson.

Best when: you want the fewest moving parts now. (Not chosen.)

4b. Fake payment — scope, swappability, state

Chosen

Build it now: interface + DB + idempotency

Working POST /payments (sleep ~300 ms → 200/402 by FAIL_RATE) behind a PaymentProvider interface; payment persists each charge to its own DB; an Idempotency-Key + UNIQUE constraint replays the original result on retry.

  • 1.2's text is this behavior; no rewrite in Phase 3.2.
  • Real provider later = add a StripePaymentProvider @Profile("real"), no edits to working code.
  • Idempotency designed in, not retrofitted — the canonical payment-safety pattern.
  • More scope than a stateless skeleton (entity, repo, service, changeset, payment DB).

Best when: you intend a real provider later and want the seams right from the start. (Chosen.)

Stateless fake, defer DB & interface

Inline fake logic in the controller, no DB, no interface; extract everything when a real provider lands.

  • Least code in 1.2; matches the field guide's "fake provider is stateless".
  • Retrofitting the interface, a DB, and idempotency later means editing working code + a migration.

Best when: payment will only ever be the curriculum's fake. (Not chosen — a real provider is planned.)

4c. Settled defaults (no fork)

  • Health: actuator /actuator/health (not a hand-rolled controller) — production standard, reused by Compose/observability later.
  • notification web server: add spring-boot-starter-web so the consumer can serve health + advertise a port. Documented deviation from "pure consumer".
  • Eureka client: starter only, no enable-annotation; clients must not disable register/fetch (those are server-only, set in discovery).
  • Hermetic tests: eureka.client.enabled: false + (catalog/booking) datasource auto-config excluded in src/test/resources.

5. Risks / microservices cost felt

Database-per-service, first contact. catalog, booking, and payment each own a private Postgres — no shared schema, no cross-service JOIN. Standing up three databases (vs. the monolith's single screenmaster DB) is the first concrete cost: more infrastructure per service. The production-grade answer here is Liquibase migrations + ddl-auto: validate (not ddl-auto=update), so each service's schema is versioned and reproducible from the start — fixing a flagged monolith gap.

Duplicate delivery / double-charge, previewed. Persisting charges raises the at-least-once problem early: a retried POST /payments must not charge twice. The answer is a client-supplied idempotency key + a UNIQUE constraint as the source of truth (catch the violation, replay the stored result). This is the synchronous twin of the Phase-4 idempotent consumer — same lesson, different trigger — so the concept compounds rather than repeats.

Partial failure, previewed. The fake payment provider with FAIL_RATE is the deliberate fault injector the saga (Phase 3) and resilience (Phase 5) phases lean on. Building it now means later phases observe failure rather than scramble to create it. The PaymentProvider interface keeps the real-provider door open without pulling that (out-of-curriculum) work forward.
