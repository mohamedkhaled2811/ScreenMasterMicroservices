1. Summary

Give the catalog service its first real tables and its first read endpoint. Today catalog boots against an empty schema (an empty Liquibase changelog, no entities). This step adds the movies / genres tables (the typo'd geners is renamed here — clean boundary) via a Liquibase changeset, the JPA entities validated against them, and GET /api/movies/{id} returning a MovieDto.

Why now: it's the prerequisite for the whole of Phase 2. Booking (2.2/2.3) needs a movie endpoint to call before we can feel the missing JOIN — there is nothing to compose or replicate until Catalog actually owns and serves movie data. This is the first service in the system to own a real domain table, so it also sets the package-by-layer + Liquibase + ProblemDetail template (mirroring payment/) that Booking will copy in Phase 3.

Scope guard: read path only — one GET. No TMDB sync, no POST/filter, no genre endpoint, no seed-from-live-TMDB job. Those are deliberately deferred (see §8). We hand-seed a handful of rows so the endpoint has something real to return.

3a. Proposed schema (grounded in TMDB)

The monolith's Movie carried a thin slice of TMDB. The task invites enriching it "based on what TMDB has." Below is the recommended set — the columns TMDB's GET /movie/{id} returns that a cinema catalog actually uses to render a movie page. Every column maps 1:1 to a real TMDB movie-details field, so a future sync job (deferred) fills them with no schema change.

movies
  id                BIGINT        PK, assigned (TMDB movie id — not generated)
  title             VARCHAR(500)  NOT NULL
  original_title    VARCHAR(500)
  overview          TEXT
  tagline           VARCHAR(1000)
  release_date      DATE                      -- TMDB "release_date" (may be null/empty upstream)
  runtime           INT                       -- minutes
  status            VARCHAR(40)               -- TMDB "status": Released, Post Production, ...
  original_language VARCHAR(10)               -- ISO-639-1, e.g. "en"
  popularity        NUMERIC(10,3)
  vote_average      NUMERIC(4,2)              -- 0.00 – 10.00
  vote_count        INT
  poster_path       VARCHAR(255)              -- TMDB relative path, e.g. "/abc.jpg"
  backdrop_path     VARCHAR(255)
  adult             BOOLEAN       NOT NULL DEFAULT false
  created_date      TIMESTAMPTZ   NOT NULL    -- our auditing (BaseEntity-style)
  last_modified_date TIMESTAMPTZ

genres
  id    BIGINT        PK, assigned (TMDB genre id)
  name  VARCHAR(120)  NOT NULL, UNIQUE

movie_genres   (join table, the @ManyToMany)
  movie_id  BIGINT  NOT NULL  FK → movies(id)
  genre_id  BIGINT  NOT NULL  FK → genres(id)
  PRIMARY KEY (movie_id, genre_id)

Notes / decisions baked in: (a) table renamed geners → genres (schema §9 cleanup — we own the boundary now, so we fix it). (b) PKs are BIGINT + assigned (no @GeneratedValue): the id is TMDB's, stable and externally sourced — exactly why §2.1 flags Catalog as a clean boundary. The monolith used int; BIGINT/Long is future-proof and costs nothing. (c) Enums-as-string convention doesn't apply — TMDB status is a free-text upstream string, so it stays a plain VARCHAR (not a JPA enum) to avoid breaking on an unexpected value. (d) FKs inside Catalog are fine — the "no cross-service FK" rule is about FKs that cross a service boundary; movie_genres is wholly owned by Catalog.

4. Decisions made

Two questions were on the table; both are now settled:

  • Schema richness → full TMDB-grounded columns (the §3a set). Every column maps 1:1 to a real TMDB GET /movie/{id} field, so the deferred sync job fills them with zero further migration. (The thinner "monolith parity" alternative was rejected — it would force a second migration the moment sync wants vote_average, runtime, etc.)
  • Seeding → none. The table ships empty; rows are populated in the next phase (the TMDB sync step). This drops the planned 002-seed-movies.yaml changeset entirely.

Consequence of shipping empty: the running endpoint returns 404 for every id until the next phase fills the table. So the happy-path 200 is proven by a test that inserts its own row (a @DataJpaTest / slice test), not by curl against the live service. Functionally nothing is lost — the 404 ProblemDetail path is fully exercisable today, and the 200 path is covered by tests; only the manual curl demo waits for real data.

6. Risks / microservices cost felt

This step doesn't solve a distributed cost — it plants the one we'll feel next. By giving Catalog sole ownership of movies in its own database, we make it impossible for Booking to JOIN a booking to a movie title. That missing JOIN is the entire point of Phase 2 (2.2 API composition vs 2.3 CQRS read model). The production-grade move here is the boundary itself: assigned external (TMDB) PKs so the id is a stable cross-service reference, a versioned schema (Liquibase + validate) so the contract can't silently drift, and DTOs so the wire shape is decoupled from the table. The cost we pay now: the table ships empty (no shared DB to INSERT … SELECT from), so until the sync step fills it the live endpoint only serves 404s — the 200 path lives in tests.
