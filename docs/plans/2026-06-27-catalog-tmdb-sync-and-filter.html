Date: 2026-06-27 Author: Claude Code + Mohamed Status: DRAFT — awaiting review
Milestone: M2 (Catalog) Service: catalog Schema §: 6 (TMDB) · §8.1 (Catalog) · §1 (MovieSpecification) Build plan: pre-2.2 data load

1. Summary

Catalog's tables (movies, genres, movie_genres) shipped empty in step 2.1 — the schema was deliberately built to mirror TMDB's GET /movie/{id} so a sync job could fill it with no further migration. This plan does exactly that, in two halves of one job:

  • TMDB sync (write side): a @Scheduled background job that pages through TMDB's discover/list endpoints, hydrates each movie via GET /movie/{id} (full details + genres), and upserts into catalog-db. Progress is tracked in a new sync_status table so a crash or rate-limit pause resumes instead of restarting.
  • Dynamic filter (read side): a new GET /movies endpoint that builds a JPA Specification from whatever query params the caller sends (title, genre, language, year, min rating…), sorts, and returns a paged Page<MovieSummaryDto>. This is the monolith's MovieSpecification pattern (schema §1), rebuilt clean.

Together they make Catalog a real, queryable service: the sync gives it data; the filter gives callers a way to find it. This is the prerequisite for everything downstream (a Booking "my bookings" page needs real movies to point at).

Explicitly out of scope (moved to a later branch): build-plan step 2.2 "My bookings" — API composition (Booking calling Catalog over RestClient and merging titles). We are only getting data into Catalog and making it queryable here. No booking module changes in this plan.

4. Options

Three decision points. The first two (sync cadence, sync scope, filter impl) were chosen up front and are recorded here as the picked options; the genuinely open trade-offs are the HTTP client and the upsert strategy.

4a — Sync cadence & scope (decided)

Chosen

A — @Scheduled + paged, resumable

A cron-driven background job pages through TMDB's list endpoints; sync_status stores last_page/total_pages per type so a crash or rate-limit pause resumes mid-walk. Each movie hydrated via GET /movie/{id} for full details+genres.

  • Production-shaped: this is how a real catalog stays fresh.
  • Resumability is the interesting lesson — mirrors the monolith's SyncStatus.
  • Respects TMDB rate limits by walking a bounded number of pages per tick.
  • Most code; needs careful idempotent upsert so re-runs don't duplicate.

Per your call: @Scheduled only (no manual trigger endpoint), discover paged + resumable.

B — Manual endpoint / small fixed set

A POST /admin/sync you fire by hand, or sync just genres + a handful of movie ids.

  • Far less code; fully deterministic for demos.
  • Skips the resumability/paging lesson that makes the sync worth building.
  • Not how a real catalog ingests — less to narrate in an interview.

Not chosen. (We can still toggle tmdb.enabled=false + run a tiny page range for a quick demo.)

4b — HTTP client for TMDB (open)

Recommended

A — RestClient (blocking)

Use Spring's synchronous RestClient, same starter Booking already pulls in (spring-boot-starter-restclient).

  • The sync runs on a @Scheduled thread — blocking is fine, no reactive glue.
  • One HTTP-client story across services (Booking → Payment/Catalog also uses it).
  • Simpler error handling; pairs naturally with the resumable loop.
  • No built-in backpressure — fine here, we bound pages per tick ourselves.

B — WebClient (reactive)

The monolith used WebClient. Pull in spring-boot-starter-webflux.

  • Matches the monolith; easy parallel page fetches if ever needed.
  • Adds WebFlux to an MVC service for no real gain on a scheduled batch.
  • We'd .block() anyway inside the scheduled job — reactive benefits unused.

4c — Upsert strategy (open)

Recommended

A — JPA save() merge on assigned id

Because PKs are assigned TMDB ids, repository.save(movie) on an existing id is an UPDATE. Re-fetch genres, re-link movie_genres, save. Genres upserted first (parents before the join).

  • Idempotent by construction — re-syncing the same page updates, never duplicates.
  • Pure JPA, portable, easy to unit-test with @DataJpaTest.
  • A read-then-write per movie (acceptable at sync batch sizes).

B — Native INSERT … ON CONFLICT

Postgres upsert for movies and the join table.

  • Fewer round-trips; one statement per row.
  • Postgres-specific SQL; harder to test on H2; bypasses JPA auditing/lifecycle.
  • Premature optimization for a learning-scale catalog.

4d — Filter implementation (decided)

Chosen

A — JPA Specifications + Pageable

GET /movies?title=&genreId=&language=&year=&minRating=&sort=&page=&size= → each present param contributes one Specification predicate, combined with .and(); Spring Data supplies Pageable sort/paging; returns a Page<MovieSummaryDto>.

  • Composes cleanly: "filter by whatever the user sends" without a method explosion.
  • Exactly the monolith's MovieSpecification pattern, rebuilt clean.
  • Paging + sorting come for free and safely (whitelist sortable fields).
  • Criteria API is more verbose than a JPQL string (offset by composability).

B — Derived queries / @Query

Hand-written repo methods per filter combination.

  • Trivial for one or two fixed filters.
  • Combinatorial explosion as filters multiply; doesn't compose.
  • Wrong fit for "dynamic by what the user sends".

5. Implementation tasks

Chosen path: 4a-A (@Scheduled, paged, resumable), 4b-A (RestClient), 4c-A (JPA save merge), 4d-A (Specifications + Pageable). Read side and write side are independent — the filter endpoint can be built and tested against seeded rows before the sync exists, and vice versa.

  1. Filter DTO + Specifications + repository wiring

    Goal: the read side first — it's lower-risk, needs no TMDB key, and proves the new query surface against a few seeded rows. Add MovieFilter, MovieSpecifications, make MovieRepository a JpaSpecificationExecutor, and a MovieSummaryDto.

    Done when: a @DataJpaTest persists a handful of movies+genres and asserts each predicate (title contains, genreId, language, year, minRating) filters correctly and composes.

    Depends on: — (existing 2.1 entities)

    Done when: a @WebMvcTest verifies param binding, the page envelope shape, a bad sort field → CATALOG_VALIDATION_ERROR ProblemDetail, and default paging when no params given.

    Depends on: Task 1

Add deps + @ConfigurationPropertiesScan; key from .env.

    Done when: a slice test deserializes captured TMDB JSON fixtures into the DTOs and maps a movieDetails response to a Movie + Genres correctly (no live HTTP call in tests).

    Depends on: —

  4. sync_status schema + entity + repository

    Goal: the resumability bookkeeping. Liquibase changeset 002 for sync_status (unique sync_type, last_page, total_pages, state, error_message, timestamps), the SyncStatus entity with STRING enums, repository. Wire into master changelog; entity must pass ddl-auto=validate.

    Done when: app boots against real catalog-db with changeset 002 applied; a @DataJpaTest persists+reads a SyncStatus row.

    Depends on: —

  5. Resumable TmdbSyncService (idempotent upsert)

    Goal: the engine. For each sync type: read/create its sync_status, fetch the next page (bounded per tick), upsert genres then movies (save()-merge on assigned id, re-link movie_genres), advance last_page, mark COMPLETED at the end / FAILED + error_message on error so the next tick resumes.

    Done when: a service test with a mocked TmdbApiClient proves: (a) running twice over the same page produces no duplicate movies/genres (idempotent), (b) a thrown error mid-walk leaves state=FAILED at the right last_page, and (c) the next run resumes from there.

    Depends on: Tasks 3, 4

  6. @Scheduled trigger + enablement guard

    Goal: drive the sync on a cron. TmdbScheduledTasks with @Scheduled(cron=${tmdb.cron}) calling the sync service, no-op when tmdb.enabled=false (default off in tests so they stay hermetic, on for local/compose). @EnableScheduling on the app.

    Done when: with a real TMDB_API_KEY, booting catalog triggers a sync that populates rows; GET /api/movies?title=... returns real TMDB movies; tests remain green with scheduling disabled.

    Depends on: Task 5

6. Risks / microservices cost felt

Owning your data means owning its ingestion. In the monolith, movies were just rows other code JOINed to. As a service, Catalog must independently keep its own database fresh from an external system — and do it resiliently: TMDB rate-limits, times out, and returns partial pages. The sync_status table is the concrete cost — a service that survives a crash mid-sync needs durable, resumable progress, not a fire-and-forget loop. This is the same eventual-consistency / partial-failure muscle the sagas and outbox exercise later, in a read-only, low-stakes setting.

  • Idempotency: a re-run must not duplicate rows — guaranteed here by assigned PKs + save()-merge. (Same lesson as the idempotent consumer in Phase 4.)
  • Secret handling: TMDB_API_KEY via .env/env var, never committed — a stated convention, enforced here.
  • Safe dynamic queries: the filter must whitelist sortable/filterable fields so a caller can't sort by an arbitrary column or inject — Specifications keep this typed and bounded.
  • Test hermeticity: no live TMDB call in CI — the API client is mocked and the scheduler is disabled under test.

8. Open questions

  • HTTP client (4b): confirm RestClient (recommended, matches Booking) vs WebClient (matches monolith).
  • Upsert (4c): confirm JPA save()-merge (recommended) vs native ON CONFLICT.
  • Which TMDB list types to sync, and the cron + pages-per-tick bound? Default suggestion: POPULAR + TOP_RATED + NOW_PLAYING, every 6h, ~3 pages/tick (≈60 movies) to stay well under rate limits.
  • TMDB auth style: v3 API key as query param, or v4 bearer token in the Authorization header? (Bearer is the modern default.)
  • Filter param surface: is title/genre/language/year/minRating/adult the right v1 set, or do you want more (runtime range, status)?
