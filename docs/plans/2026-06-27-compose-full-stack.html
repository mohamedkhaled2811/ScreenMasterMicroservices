1. Summary

This is the final step of Phase 1 (field guide M1). Steps 1.1–1.3 built the six services (discovery/Eureka, gateway, catalog, booking, payment, notification) and verified each boots and that the gateway routes through lb:// — but only by running pieces by hand against localhost. 1.4 brings the whole topology up with one command (docker compose up --build): every service containerised, database-per-service made physical (each owning service gets its own Postgres container), and service name = DNS name on the Compose network. The current compose.yaml is a leftover single-Postgres monolith stub and is replaced entirely. This is the lesson that the talk-track "I run a multi-service system locally with isolated databases — here's the compose file" comes from.

The "two Postgres → three" drift (decided with Mohamed)

BUILD_PLAN 1.4 and the concept doc both say "two Postgres (catalog-db, booking-db)" — they were written when payment was planned to be DB-less. But the payment service as built in 1.2 ships a real payments table via Liquibase with ddl-auto=validate, so it needs its own database to boot. We follow the code (truest to database-per-service) and add payment-db — three Postgres total — and fix the stale docs.

The multi-stage Dockerfile (built from repo root)

# ---- build stage: compile this module (+ its deps) inside the image ----
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY . .
# -pl <module> -am = build the module and the modules it depends on
RUN ./mvnw -q -pl <module> -am clean package -DskipTests

# ---- runtime stage: slim JRE + the repackaged jar ----
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/<module>/target/<module>-*.jar app.jar
EXPOSE <port>
ENTRYPOINT ["java","-jar","/app.jar"]

Root build context. Because each Dockerfile needs the parent pom and the mvnw wrapper, Compose uses build: { context: ., dockerfile: <svc>/Dockerfile } (context = repo root), not the concept doc's build: ./booking shorthand (which assumes a self-contained module). -DskipTests in the image: the reactor build already gates tests; the image stage is for packaging, not re-running the suite.

The Eureka-under-Compose fix (env-only, no code change)

Clients currently set no eureka.instance.hostname, so each registers under its container hostname (a random hash) that other containers can't resolve — lb://catalog would hand the gateway an unreachable address. Fix per app service via an injected env var (Spring relaxed binding, no YAML edit):

EUREKA_INSTANCE_PREFER_IP_ADDRESS=true   # register the container's Compose-network IP

This makes lb:// resolve to a routable 172.x address on the Compose bridge network. (Alternative EUREKA_INSTANCE_HOSTNAME=<service-name> is noted in Option C.)

Out of scope (later phases)

No RabbitMQ/Zipkin wiring in services (Phase 4 / Phase 6 — the containers run but nothing connects yet), no Keycloak/identity (Phase 7), no edge auth or rate-limiting (Phase 7).

4. Options

Three axes had a real choice. Axis 1 (payment DB) and axis 2 (image build) were decided with Mohamed and are baked into the recommended path; axis 3 (Eureka identity) is shown for completeness.

Recommended

Option A — 3 Postgres · multi-stage Dockerfiles · rabbit+zipkin now

Each owning service gets its own Postgres; images build inside Docker; the broker and tracing containers run from day one (unused until Phases 4/6).

  • Truest to database-per-service — payment's payments table boots against its own DB.
  • docker compose up --build is fully self-contained — no host ./mvnw step, no host-JDK dependency.
  • Topology is complete — later phases just wire to containers that already exist.
  • Three Postgres + rabbit + zipkin idle = more memory than a minimal stack.
  • First image build is slow (Maven resolves deps inside each build stage).

Best when: you want the real M1 system and faithful service boundaries — our case.

Option B — shared Postgres · pre-built jars · defer rabbit/zipkin

One Postgres with three logical databases; slim FROM jre, COPY target/*.jar Dockerfiles needing a host ./mvnw package first; add broker/tracing only in their phases.

  • Leanest stack — fewest containers, fastest up.
  • Tiny Dockerfiles, fast image builds.
  • Shared Postgres weakens the database-per-service lesson (shared blast radius).
  • Two-step build (host package, then compose) — depends on host JDK 21.
  • Diverges from the 1.4 line (which names rabbit + zipkin).

Best when: optimising for a fast inner loop over fidelity — not our goal here.

Option C — register by hostname instead of IP

Same as A, but the Eureka fix uses EUREKA_INSTANCE_HOSTNAME=<service-name> instead of PREFER_IP_ADDRESS=true.

  • Registry shows friendly DNS names (catalog) instead of 172.x IPs.
  • Must set a distinct hostname per service (more env wiring, easy to mismatch).
  • Relies on Compose DNS for service-to-service hops; IP is more robust on a single bridge network.

Best when: readable registry entries matter more than minimal config. We pick IP (A).

6. Risks / microservices cost felt

This step surfaces the operational cost of distribution: a request now crosses a container network with independent lifecycles. Two concrete costs we handle the production-grade way:

  • Startup ordering / partial readiness — app services race their database and the registry. We don't sleep; we use healthcheck + depends_on: { condition: service_healthy } so a service starts only once its DB answers pg_isready.
  • Service identity on a virtual network — discovery's whole job (return a reachable address) breaks if a service registers an unroutable container hostname. The PREFER_IP_ADDRESS fix is the small, real lesson in how discovery and the network layer have to agree. (See service-discovery.md.)

Database-per-service is also made physical here: three Postgres containers, no shared schema — the isolation the whole project argues for, now visible in docker ps.
