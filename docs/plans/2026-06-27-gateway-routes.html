1. Summary

Turn the gateway module (currently empty scaffold + pom) into a running Spring Cloud Gateway (webmvc) app on port 8080 — the single public front door. It resolves backend services through Eureka with lb:// and routes three external path families to them: /api/movies/** → catalog, /api/bookings/** → booking, /api/payments/** → payment. This teaches the M1 lesson: clients learn one address, and the cross-cutting edge concerns (routing now; edge auth + rate limiting later in M7) live in one place instead of in every service. It completes the last service-wiring step before the Compose file (1.4) stands the whole system up.

Sample of the routes block (Option A — recommended — shown):

spring:
  cloud:
    gateway:
      server:
        webmvc:
          routes:
            - id: catalog
              uri: lb://catalog
              predicates: [ "Path=/api/movies/**" ]
              filters:    [ "StripPrefix=1" ]      # /api/movies/7 -> /movies/7
            - id: booking
              uri: lb://booking
              predicates: [ "Path=/api/bookings/**" ]
              filters:    [ "StripPrefix=1" ]
            - id: payment
              uri: lb://payment
              predicates: [ "Path=/api/payments/**" ]
              filters:    [ "StripPrefix=1" ]      # /api/payments -> /payments (matches PaymentController)

4. Options

Two independent decisions: (I) how to reconcile the /api edge prefix with the services' bare paths, and (II) where the route config lives. Decision I is the one that matters — payment already serves POST /payments, not /api/payments.

Decision I — the /api prefix mismatch

Recommended

A — StripPrefix=1 at the gateway

Gateway strips the leading /api segment and forwards the rest. Services keep bare paths (/payments, /movies, /bookings).

  • The /api namespace is purely an edge concern — services don't know the public URL shape.
  • Matches the existing PaymentController (/payments) with zero service changes.
  • One stock filter; the concept doc already names filters as where request transforms live.
  • A request's external path ≠ internal path — one indirection to remember when debugging.

Best when: you want the public API contract owned at the edge (the textbook gateway role).

B — services own the full /api/... path

No filter. Re-map every controller to the full path (@RequestMapping("/api/payments")), gateway forwards verbatim.

  • External path == internal path — nothing to mentally strip when reading logs.
  • Routing config is filter-free.
  • Bakes the edge namespace into every service — the /api convention leaks across all boundaries.
  • Requires editing PaymentController now and every future controller — re-opens shipped code.

Best when: there is no gateway and clients hit services directly (not our case).

C — RewritePath regex

RewritePath=/api/payments/?(?<seg>.*), /payments/${seg} per route.

  • Most flexible — arbitrary path reshaping if the mapping ever stops being a clean prefix.
  • Regex ceremony for what is a simple one-segment strip today — harder to read.
  • YAGNI for M1; nothing here needs non-prefix rewriting.

Best when: the external→internal mapping is genuinely non-trivial. Keep in back pocket.

Decision II — where route config lives

Recommended

D — declarative YAML routes

Routes in application.yml under spring.cloud.gateway.server.webmvc.routes.

  • Matches the concept doc's sample verbatim — consistent learning surface.
  • No Java to maintain; routes are reviewable config, diff-friendly.
  • Easy to override per-environment via Compose env vars in 1.4.
  • Conditional/dynamic routing logic would need code — fine, we have none.

Best when: routes are static path→service maps (exactly our case).

E — Java RouteLocator bean

Build routes programmatically in a @Configuration class.

  • Full programmatic control; testable as a bean.
  • More code than the problem needs; diverges from the concept doc sample.
  • Harder to skim than a YAML table.

Best when: routes depend on runtime conditions. Not us.

5. Risks / microservices cost felt

Partial failure & discovery indirection. The gateway resolves lb://catalog through Eureka — so a request can now fail in new ways the monolith never had: the target service is down, or hasn't registered yet, or Eureka itself is unreachable. Routing through lb:// (not a hard-coded host) is the production-grade answer: the gateway load-balances across healthy registered instances and a freshly started service becomes reachable without editing gateway config. We'll feel the failure mode directly in Phase 5 (docker stop payment → the gateway route to payment fails fast) and the recovery when it re-registers. Note: this is the edge path only — internal Booking→Payment calls bypass the gateway and resolve via discovery directly, per the concept doc's "what does NOT go through the gateway."
