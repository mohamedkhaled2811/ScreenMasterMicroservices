Plan: TMDB Incremental Sync — /movie/changes

Date: 2026-06-30 Author: Claude Code + Mohamed Status: APPROVED — Option A implemented (cursor = dedicated CHANGES row; first-run lookback = 14 days; refresh same tick after backfill, capped)
Milestone: M2 — Catalog service Service: catalog Schema §: Catalog (Movie/Genre) Pattern: incremental / change-data sync

1. Summary

The current TMDB sync is a one-time backfill that goes dormant. Each SyncType (POPULAR / TOP_RATED / NOW_PLAYING) is paged once; when its SyncStatus reaches lastPage ≥ totalPages it is marked COMPLETED and TmdbSyncService.syncType() returns early on every future tick. So after backfill we never re-fetch a movie: rating, popularity, overview, poster and status changes on TMDB are frozen in our catalog. Only the genre vocabulary stays fresh (it is re-upserted unconditionally each tick).

This feature adds an incremental freshness path built on TMDB's GET /movie/changes endpoint — a purpose-built change feed that lists the ids of movies edited in a given UTC date window. Instead of blindly re-walking ranked lists (which re-rank constantly and would still miss off-list edits), we ask TMDB "which movie ids changed since we last looked?", then re-hydrate only those ids that we already store. This is the production pattern for keeping a downstream replica current cheaply — and it directly teaches the change-data-capture / incremental-sync lesson the field guide raises around data duplication across service boundaries.

3. What changes

The incremental path reuses the existing hydrate/upsert machinery (CatalogUpserter.upsertPage already idempotently UPDATEs by TMDB id). The new surface is a change-feed client call, a cursor to remember "how far we've caught up", and a refresh pass that runs after backfill is complete.

4. Options

All three keep the existing backfill untouched; they differ in how the cursor is modeled and when the refresh runs. The TMDB endpoint is the same in each.

Recommended

Option A — Date-cursor refresh, gated on backfill-complete

A single global "changes" cursor (last UTC day caught up). Each tick, after all list types are COMPLETED, walk /movie/changes for the window (cursor, today], intersect with ids we already store, re-hydrate those, advance the cursor by one day at a time so a crash resumes mid-window.

  • Smallest, most honest model: one cursor = "fresh through day X"; resumable like the existing walk.
  • Cheap — only re-fetches ids we own that actually changed; ignores TMDB's millions of untracked movies.
  • Backfill stays the priority; refresh only kicks in once the catalog is filled (no contention for the rate budget).
  • Needs a one-day-granularity loop + lookback clamp (TMDB only serves ~14 days of changes).

Best when: we want true freshness with minimal API cost and a resumable cursor — the production pattern.

Option B — Changes as a 4th SyncType, page-cursor reused

Add CHANGES to the enum and shoehorn it into the existing SyncStatus(page,totalPages) walk, re-querying a fixed rolling window (e.g. last 24h) each tick and paging through it like a list.

  • Maximal code reuse — almost no new control flow; rides the existing per-type loop.
  • Semantic mismatch: a page cursor that "completes" doesn't model "caught up through date X"; needs constant resetting.
  • Either misses edits (if the window is too short between ticks) or re-does work (if it overlaps) — no clean exactly-once.
  • Overloads isComplete() meaning; muddies the resumable-walk concept doc.

Best when: we cared only about minimal diff and accepted a fuzzy window. Not recommended.

Option C — Webhook / push instead of polling

Skip /movie/changes polling; have TMDB push change events to us.

  • Near-real-time; no polling cadence to tune.
  • TMDB offers no general per-movie webhook to arbitrary consumers — not actually available.
  • Needs a public ingress + signature verification + replay handling — out of scope (no Kubernetes / no public endpoint in this lab).

Best when: a real provider offered webhooks. Listed for completeness; infeasible here.

6. Risks / microservices cost felt

Data duplication across a boundary → staleness & eventual consistency. Catalog keeps a replica of TMDB's source-of-truth data. Replicas drift the moment the upstream changes; the cost is keeping them current without re-copying everything. This feature surfaces that cost and answers it the production way — a change feed + cursor (incremental, at-least-once, idempotent re-hydration) instead of a full re-scan. Concrete risks to handle:

  • Bounded change history: TMDB only serves ~14 days of /movie/changes. If the service is down longer than the lookback, the cursor can't catch up via changes alone — we clamp the window and accept that gap (a periodic full re-walk could backstop it, out of scope here).
  • At-least-once, not exactly-once: day-window overlap can re-fetch an id; safe because upserts are idempotent (PK = TMDB id → UPDATE).
  • Partial failure mid-window: the per-day cursor + per-batch transaction means a crash resumes from the last good day, never restarts the window.
  • Rate-limit back-pressure: reuse the existing per-run cap so a high-churn day degrades gracefully across ticks instead of hammering TMDB.

8. Open questions

  • Cursor home: store the changes cursor as a new field on a dedicated SyncStatus row (e.g. a CHANGES SyncType), or as a separate single-row table? A dedicated row reuses the entity but stretches the "page walk" semantics of the other rows. Lean: dedicated CHANGES row, page fields unused / nullable.
  • Refresh frequency: run syncChanges() every tick (currently every minute per application.yml cron 0 * * * * *), or on a slower cadence than backfill? Lean: same tick, but only after backfill-complete + capped per run.
  • First-run window: on the very first changes pass (cursor null), how far back do we go? TMDB caps at ~14 days. Lean: default changes-lookback-days = 1 (just "since yesterday"); larger only if we want to catch edits made during backfill.
  • Adult filter: /movie/changes includes an adult flag; do we honor the existing adult handling when refreshing, or refresh whatever we already store regardless? Lean: refresh only ids we already store, so the original filter already applied.
  • Long-downtime backstop: do we want a periodic full re-walk (reset list cursors) to cover gaps longer than TMDB's 14-day change history, or accept that as a known limitation for the lab? Lean: out of scope; note it as a limitation.
