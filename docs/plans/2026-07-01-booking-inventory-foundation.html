1. Summary

Booking is the core service and, per the build plan, it absorbs the monolith's Theater and Scheduling contexts (theaters, screens, seats, seat_types, showtimes) on top of its own bookings / booking_seats. This first part builds that write-side foundation: the JPA model, the Liquibase schema, and the admin/read CRUD for theaters → screens → seats → seat-types and for showtimes. It is the immutable facts layer the Phase-3 booking saga will read once and snapshot — so it must exist before either "my bookings" endpoint (parts 2 & 3) or the saga (Phase 3) has anything real to work with.

The microservices lesson it sets up: the booking transaction that was one ACID statement in the monolith now spans what would have been three services (Theater, Scheduling, Booking). We deliberately collapse Theater + Scheduling into Booking (build-plan decision) so the seat-uniqueness invariant stays strongly consistent inside one DB — and this part is where that collapsed inventory model is laid down.

3. The cross-service cuts this realizes

What were FK associations in the monolith become id columns the moment these tables move into Booking's private DB. Intra-Booking relations (theater→screen→seat) keep their FKs — the rule is about FKs that cross a service boundary, not these.

Scope of THIS part: the inventory tables + showtimes + their CRUD. The bookings / booking_seats tables and any booking-create logic are not in this part — they're the subject of the open decision in §8 (covered fully in part 2 or in Phase 3). This keeps part 1 a clean, testable "inventory service inside Booking" with no saga concerns.

5. Options

The decisions specific to this part. (The cross-part decisions — how bookings get created, and the CQRS publisher — live in parts 2/3 and §8 below.)

Decisions made (implemented): 5A full inventory + showtimes · 5B explicit seats + grid generator · 5C option 2 — validate movieId against Catalog synchronously on showtime-create (Mohamed's choice, the non-recommended option). §8: bookings/booking_seats tables created here (schema only, changeset 003); read endpoints take userId as a path param until Phase 7; priceMultiplier kept on SeatType.

Consequence of 5C-2, recorded honestly: showtime creation now has temporal coupling on Catalog (Catalog down ⇒ POST /showtimes returns 503 BOOKING_CATALOG_UNAVAILABLE); a bogus movieId is rejected at create time with 404 BOOKING_MOVIE_NOT_FOUND rather than lingering as an orphan. The "feel the cut at read time" lesson from the recommended path is traded for "reject the bad reference at write time".

5A · How much inventory CRUD?

Recommended

Full inventory + showtimes

All five entities with create/list/delete + showtime CRUD — the complete Theater+Scheduling foundation.

  • Matches the locked decision; the saga (Phase 3) and both read endpoints have real, seedable data.
  • Front-loads the boring schema work once, so Phases 2–3 stay focused on the distributed lessons.
  • Lets us seed a realistic fixture (1 theater, 2 screens, ~40 seats, a few showtimes) for demos.
  • Largest of the three parts; ~5 entities × (repo+service+controller+dto+tests).

Best when: you want the foundation done properly once (this is the chosen path).

Showtimes + seats only

Skip theater/screen/seat-type admin endpoints; build only what a booking strictly needs to read.

  • Smaller; faster to "my bookings".
  • Seats need a screen and seat-type to exist — you end up seeding them by hand anyway.
  • Leaves a half-built inventory model we revisit later; against "build it right the first time".

Best when: time-boxed and willing to seed inventory via SQL. (Not chosen.)

5B · Seat layout — explicit rows or a generator?

Recommended

Explicit seat rows + a "generate grid" helper

Seats are first-class rows (POST /theaters/screens/{id}/seats); plus one convenience endpoint that bulk-creates an R×C grid for a screen so seeding a demo isn't 40 calls.

  • Mirrors the monolith (per-seat rows with (screen, row, number) uniqueness) — needed for the per-seat booking guard later.
  • The generator keeps demos one-command without faking the data model.
  • Slightly more surface (one extra endpoint).

Best when: seats must be individually reservable (they must, for Phase 3).

Seats as a count on the screen

Store seatCount, no per-seat rows.

  • Tiny schema.
  • Breaks the Phase-3 double-booking guard (you reserve specific seats, not a count).
  • Diverges from the schema doc; we'd rebuild it for the saga.

Best when: never, for this project. (Not chosen.)

5C · Does Showtime validate movieId against Catalog at create time?

Recommended

No sync check now — store the id, validate lazily

Accept any movieId on showtime create; trust it's a real Catalog id. The title is resolved later (parts 2/3). This is the honest database-per-service stance.

  • No temporal coupling: you can create showtimes even if Catalog is down (write path stays available).
  • Sets up M2 cleanly — the "missing JOIN" only bites when we render titles, exactly where we want to feel it.
  • A typo'd movieId is only caught at read time (acceptable; surfaces as a known gap).

Best when: you want to feel the cut, not paper over it. (Aligns with sync-vs-async heuristic: don't go sync unless you must.)

Validate via a synchronous Catalog call on create

RestClient GET /api/movies/{id} before persisting the showtime.

  • Bad movieId rejected immediately.
  • Introduces temporal coupling on the write path — Catalog down ⇒ can't schedule.
  • Premature: it's the part-2 composition concern arriving early, in the wrong place.

Best when: you treat the reference as a hard invariant — we don't, by design.

6. Implementation tasks (recommended path)

Build bottom-up: schema → entities (validate against schema on boot) → repos → services → controllers → tests. Each task is independently checkable.

  1. Liquibase changesets for inventory + showtimes

    Goal: own the schema in 001-create-inventory.yaml and 002-create-showtimes.yaml; wire both into the master changelog. Encode the unique constraints (screens(name, theater_id), seats(screen_id, row, number), seat_types(name), showtimes(screen_id, movie_id, show_date, show_time)) and the intra-Booking FKs. movie_id is a plain indexed column — no FK.

    Done when: ./mvnw -pl booking liquibase:update (or app boot) creates all five tables on a clean Postgres.

    Depends on: —

  2. JPA entities + enums (STRING)

    Goal: map the five entities. ScreenType and ShowtimeStatus are @Enumerated(STRING) (the schema doc flags both as fragile ordinals). Lazy @ManyToOnes; open-in-view: false already set, so fetch deliberately (EntityGraph or explicit queries) — no LazyInitializationException.

    Done when: app boots with ddl-auto=validate green (entities ⇄ schema agree); a @DataJpaTest persists a theater→screen→seat→seat-type graph and a showtime, and the unique constraints reject a duplicate.

    Depends on: Task 1

  3. Error contract (BookingErrorCode + handler)

    Goal: stand up the exception/ package exactly like payment/: a BookingErrorCode enum (BOOKING_VALIDATION_ERROR, BOOKING_THEATER_NOT_FOUND, BOOKING_SCREEN_NOT_FOUND, BOOKING_SHOWTIME_NOT_FOUND, BOOKING_DUPLICATE, BOOKING_INTERNAL_ERROR), a base BookingException carrying a code, typed not-found exceptions, and one GlobalExceptionHandler rendering RFC 9457 ProblemDetail with a code property.

    Done when: a deliberate 404 returns application/problem+json with the right code in a @WebMvcTest.

    Depends on: — (parallel with 1–2)

  4. Theater / Screen / Seat / SeatType service + controller

    Goal: CRUD for the inventory tree. Endpoints (bare paths; /api stripped at gateway): list/create/delete theaters; list/create/delete screens of a theater; list/create/delete seats of a screen + the bulk grid generator (5B); list/create/delete seat-types. Validate parent existence and uniqueness; throw coded exceptions — never return an error from a controller.

    Done when: curl through the gateway creates a theater→screen→seats→type and lists them back; duplicates → BOOKING_DUPLICATE; missing parent → the right not-found code.

    Depends on: Tasks 2, 3

  5. Showtime service + controller

    Goal: create/get/delete showtimes and read them by movie and by screen (the monolith's /show-time/movie/{id}, /screen/{id}, upcoming-by-movie). Create validates the screenId exists (intra-Booking) but not the movieId (5C); enforce the slot-uniqueness constraint.

    Done when: a showtime is created against a real screen with a movieId + basePrice; GET /showtimes/movie/{id} returns it; a clashing slot → BOOKING_DUPLICATE.

    Depends on: Tasks 2, 3, 4

  6. Demo seed + build-plan update

    Goal: a small optional Liquibase seed changeset (gated/labelled so it's clearly demo data, not production) or a documented curl script that creates one theater, two screens, a seat grid, two seat-types, and a few showtimes pointing at real synced Catalog movie ids — so parts 2/3 and Phase 3 have data. Update BUILD_PLAN.md with the new step + tick.

    Done when: one command stands up a demo cinema; BUILD_PLAN.md reflects the step.

    Depends on: Tasks 4, 5

7. Risks / microservices cost felt

Cost surfaced: the distributed transaction, set up (not yet paid). By pulling Theater + Scheduling into Booking, the seat-availability invariant stays strongly consistent in one DB — this is the production answer to schema §8.3 option 1 ("keep seat-reservation state inside Booking"). The plan also realizes the first FK cut: Showtime → Movie becomes a bare movie_id. We feel nothing yet — that's the point: the cut is dormant until part 2 tries to render titles and discovers the JOIN is gone. We deliberately resist "fixing" it with a sync call at create time (5C), so the lesson lands where it should.

  • Orphan movie_id: a showtime can point at a non-existent movie. Accepted; becomes visible in part 2 and is a talking point ("referential integrity is now my job, not the DB's").
  • Enum migration debt avoided: we store STRING from day one, so we never inherit the monolith's ordinal-corruption risk.

8. Open questions — RESOLVED

All three taken as recommended. Bookings tables: created here (changeset 003) as schema-only, unmapped tables — no Booking/BookingSeat entity yet, so ddl-auto=validate ignores them; they're mapped and written in Phase 3. Auth: read endpoints take userId as a path param for now (none needed in this part yet — arrives with part 2's "my bookings"). Pricing: priceMultiplier kept on SeatType.

  • Bookings table location. Do bookings/booking_seats get their schema here (so parts 2/3 can seed/read them) or only in Phase 3? Recommendation: create the tables here (changeset 003) but no booking-create logic — that keeps the schema cohesive and lets part 2 seed rows, while the saga that writes them stays in Phase 3. This is the cross-part decision you asked to "decide in the plan"; part 2 elaborates the two paths (minimal-create vs seed).
  • Auth. userId on a booking comes from the JWT in Phase 7. Until then, do read endpoints take userId as a path param (monolith style) or a header? Recommendation: path param now, swap to the authenticated principal in Phase 7 (flagged as the schema-§9 TODO).
  • Seat-type pricing. Keep the monolith's priceMultiplier on SeatType (total = basePrice × multiplier)? Recommendation: yes — preserves the documented pricing rule the saga will snapshot.
