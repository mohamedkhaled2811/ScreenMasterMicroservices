1. Summary

Build the first answer to a cross-service query. "Show me my bookings, with the movie title for each." Booking owns the bookings; Catalog owns the titles; the JOIN that used to do this is gone. Way A — API composition: Booking's GET /bookings/user/{userId} reads its own rows, collects the distinct movieIds, calls Catalog over HTTP (RestClient, load-balanced via lb://catalog) to fetch those titles, and merges them in memory into the response. This is BUILD_PLAN step 2.2, and the whole point of M2: you write the JOIN yourself, in application code, over the network — and you feel what that costs when Catalog is slow or down.

3. Prerequisite — bookings must exist to read

"My bookings" reads bookings + booking_seats. Part 1 creates those tables (open-question recommendation), but real booking creation is the Phase-3 saga. So before way A returns anything meaningful, rows must get there. This is the cross-part decision you asked to settle in the plan — laid out as the two options below (§4A). Way A's composition logic is identical either way; only how rows arrive differs.

Each booking row already carries showtimeId; each showtime carries movieId. So the title lookup is: booking → showtime.movieId → Catalog GET /movies/{id} → title. We can avoid a second hop by snapshotting movieId (and movieTitle at booking time) onto the booking row — see §4B, a genuine design fork for how "composition" even applies.

4. Options

4A · How do booking rows come to exist for this endpoint?

Recommended

Minimal POST /bookings now (no saga)

A basic create: validate showtime+seats exist, run the local double-booking guard, snapshot seat price + showtime facts, persist PENDING + booking_seats. No Payment call, no compensation — that orchestration is Phase 3.2, layered on top of this.

  • Realistic data: "my bookings" reads rows a user actually created via the API.
  • Builds Phase-3's 3.1 ("Booking core: create PENDING, hold seats") early — minimal rework, the saga just wraps it.
  • Exercises the seat-uniqueness invariant (the one place that stays strongly consistent).
  • Some overlap with Phase 3.1; we must avoid baking saga assumptions in prematurely.

Best when: you want the read endpoint demoed on real, self-created data (chosen unless you prefer to keep Phase 2 read-only).

Seed rows via a Liquibase fixture

A demo-only changeset inserts a handful of bookings + booking_seats so the read path has something to return. No write endpoint yet — all booking creation stays in Phase 3.

  • Keeps Phase 2 strictly about the read/composition lesson; zero write logic.
  • Smallest change; no overlap with the saga.
  • The data is fake; the demo is less convincing ("where did these bookings come from?").
  • Still need a clean way to gate seed data out of any real run.

Best when: you want to defer all write logic and keep parts 2/3 laser-focused on composition vs CQRS.

4B · What does Booking snapshot vs look up live?

Recommended

Snapshot movieId; look up title live

Store movieId on the booking (copied from the showtime at create time) so Booking doesn't need a showtime join to know which movie. The title is fetched live from Catalog per request — that's the composition we want to feel. (Optionally also snapshot the title-at-time for an audit/fallback field, but render the live one.)

  • Keeps the M2 lesson intact: the cross-service call is real and on the hot path.
  • Title stays fresh (renamed movie shows new title) — the upside of composition over a stale read model.
  • Sets up the part-3 contrast precisely (way B trades this freshness for availability).
  • Every "my bookings" hit calls Catalog; latency + a failure mode (handled in §6).

Best when: you want composition to actually bite (chosen — it's the lesson).

Snapshot the title too; never call Catalog

Copy the title onto the booking at create time and just return it — no runtime Catalog call.

  • Fastest, fully available read; no dependency on Catalog at read time.
  • There's no composition left to demonstrate — defeats the purpose of way A.
  • Titles go stale and never refresh (this is basically a frozen read model, the worst of both).

Best when: never for way A — but note it's a legitimate production pattern for immutable facts (price), just not for a mutable title.

4C · One-by-one or batch the Catalog lookup?

Recommended

Batch: one call for the distinct ids

Collect the page's distinct movieIds and fetch them together — reuse Catalog's existing GET /movies?ids=… filter, or add a tiny GET /movies/batch?ids=1,2,3. Build an id → title map, then merge.

  • One network round-trip per page, not N — the obvious N+1 fix, and a great talking point.
  • Latency stays flat as the booking list grows.
  • May need a small batch endpoint on Catalog (cheap; or reuse the filter's id in (…)).

Best when: always — this is the production-grade composition.

Per-booking GET /movies/{id}

Call Catalog once per booking row.

  • Uses the existing endpoint as-is; zero Catalog change.
  • Classic N+1 over the network — pages of bookings = pages of calls.
  • We'd build it just to immediately call it a smell; better to do it right and name the smell.

Best when: a deliberate teaching detour to measure N+1 first, then fix. Optional.

6. Risks / microservices cost felt — this is the lesson

Cost surfaced: the missing JOIN + partial failure. The JOIN is now hand-written network code. The sharp edge: what happens when Catalog is down or slow? Way A's honest answer is "the page degrades or fails" — and we make that explicit rather than letting it hang:

  • Timeout on the RestClient (a short connect/read timeout) so a dead Catalog fails fast instead of hanging the request.
  • A decision to make: on Catalog failure, do we (a) fail the whole page with a coded BOOKING_CATALOG_UNAVAILABLE ProblemDetail, or (b) degrade — return the bookings with movieTitle: null / a placeholder, log the gap? Recommendation: degrade — a booking list with missing titles is more useful than a 502, and it sets up the part-3 contrast beautifully ("way B wouldn't even notice Catalog was down"). Either way the behavior is intentional, not an accident.
  • Phase-5 hook: the real Resilience4j retry/circuit-breaker around this exact client is Phase 5. Here we do the minimum honest version (timeout + explicit degrade) and note the breaker as the next step — we don't gold-plate ahead of its milestone.
  • N+1: addressed by 4C-A (batch). Worth saying out loud as the thing composition gets wrong by default.
