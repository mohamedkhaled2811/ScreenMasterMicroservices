1. Summary

The second answer to the same cross-service query — and the opposite trade. Instead of calling Catalog at read time, Catalog publishes a MovieUpdated event to RabbitMQ whenever a movie changes, and Booking keeps its own local movie_titles(id, title) table, updated by a consumer. Now "my bookings" is a local JOIN again — Booking joins its bookings to its own title cache, no network call. This is BUILD_PLAN 2.3 and a small, honest CQRS read model: writes stay with the owner (Catalog), heavy reads hit a denormalized local view. Then 2.4 ("break it"): stop Catalog — way A (part 2) fails or degrades; way B keeps serving titles, possibly stale. That single side-by-side is the entire eventual-consistency lesson, felt.

Per the locked decision, this plan covers both sides: the Catalog publisher and the Booking consumer + read model.

3. The shape

Catalog (owns movies)                         RabbitMQ                      Booking (read model)
  upsert movie ──▶ publish MovieUpdated ──▶ [exchange] ──key──▶ [queue] ──▶ consumer ──▶ UPSERT movie_titles(id,title)
                   {id, title, eventId}                                                         │
                                                                                                ▼
                       GET /bookings/user/{id}  ──▶  LOCAL JOIN bookings ⨝ movie_titles  (no network call)

The contrast with part 2: way A reaches across the boundary at read time (fresh, but coupled); way B reaches across ahead of time via events (decoupled at read time, but the local copy lags).

4. Options

4A · How reliably does Catalog publish? (publisher side)

Recommended

Direct publish now; full outbox in Phase 4

Catalog publishes MovieUpdated straight from the upsert path (RabbitTemplate.convertAndSend) after a successful save. Note the gap honestly: if the broker is down at that instant the event is lost — which is exactly the problem the transactional outbox solves in Phase 4. We build the naive version here so M4's outbox has a felt motivation.

  • Small, focused on the M2 CQRS lesson; doesn't pull Phase-4 work forward.
  • The "lost event" gap is a deliberate, narratable setup for the outbox.
  • Not reliable: a publish can be lost on broker hiccup (acknowledged, deferred to M4).

Best when: you want way B working without conflating it with the outbox milestone (chosen).

Outbox in Catalog now

Write MovieUpdated to a Catalog outbox table in the same txn as the upsert; a relay publishes it.

  • Reliable from day one; no lost events.
  • Pulls Phase-4's whole pattern into Phase 2; larger, and steals M4's punchline.
  • The build plan explicitly sequences the outbox at M4 — jumping it muddies the curriculum.

Best when: you'd rather never ship the naive version. (Against the build-plan sequencing.)

4B · How does Booking consume idempotently? (consumer side)

Recommended

UPSERT keyed by movie id (naturally idempotent)

The consumer does INSERT … ON CONFLICT(id) DO UPDATE into movie_titles. Re-delivering the same MovieUpdated just re-writes the same row — idempotent by the key, no dedupe table needed for a last-writer-wins title cache.

  • Simplest correct thing: the operation is intrinsically idempotent (matches catalog's own assigned-key upsert pattern).
  • No processed_events table to maintain at this stage.
  • Out-of-order delivery could write an older title over a newer one (mitigate with an updatedAt/version on the event — see §6).

Best when: the projection is last-writer-wins (a title cache is). The full processed_events dedupe is the Phase-4 lesson.

processed_events dedupe table now

Track each consumed eventId; skip duplicates explicitly.

  • The general idempotent-consumer pattern, reusable for non-idempotent side effects.
  • Overkill for an idempotent UPSERT; it's the M4 (Notification) lesson, better taught there with the email send-effect.

Best when: the side effect isn't naturally idempotent (Phase 4's email). Here, not needed.

4C · What seeds the read model for movies that changed before Booking existed?

Recommended

Lazy backfill on miss (fallback to a Catalog fetch)

If a booking's movieId isn't in movie_titles yet (no event seen for it), fetch it once from Catalog (reusing part 2's CatalogClient) and cache it locally. Steady-state reads are local; first-ever read of an un-cached movie does one lookup.

  • No cold-start hole — the read model fills itself on demand and from events.
  • Reuses part 2's client; shows composition + CQRS composing (a real production pattern).
  • A cache-miss read still touches Catalog (so "break it" must use an already-cached movie to show way B surviving — which is the honest demo anyway).

Best when: you want no missing titles ever, with local reads in steady state (chosen).

Catalog emits a full snapshot / Booking ignores misses

Either Catalog publishes all current movies once on startup, or Booking just shows "(title unavailable)" for misses.

  • Pure event-driven; no read-time Catalog call at all.
  • Snapshot-on-startup is more publisher machinery; "ignore misses" leaves visible holes until an event arrives.

Best when: you want way B to be 100% network-free even on cache miss, and accept holes or a snapshot job.

6. Risks / microservices cost felt

Cost surfaced: eventual consistency, by choice. The local movie_titles table lags the real Catalog by however long the event takes to arrive. A movie renamed in Catalog shows the old title in "my bookings (way B)" until the event lands — and that's a business decision, not a bug (database-per-service.md). The flip side is the prize: with Catalog down, way B still answers from the local copy. That's the whole 2.4 demo.

  • Lost event (publisher gap): direct publish can drop on broker hiccup → the read model silently misses an update. Mitigated by 4C lazy-backfill (a miss self-heals) and fully solved by the Phase-4 outbox. Named, not hidden.
  • Out-of-order / duplicate delivery: the UPSERT is idempotent (4B-A); carrying updatedAt on the event lets the consumer ignore an older write (last-writer-wins by timestamp), avoiding a stale overwrite.
  • Two ways coexisting: keeping way A and way B both live (separate endpoints) is intentional — 2.4's value is running them against the same stopped Catalog and watching them diverge.
  • Scope honesty: this is a light CQRS read model (a title cache), not an Elasticsearch projection. We say that out loud; the pattern is the lesson, not the scale.

9. Decisions — RESOLVED (grill session 2026-08-03) & IMPLEMENTED

Every open question below was walked in a grilling session and locked. Two were pushed back on and re-shaped (the ambiguous four-field payload; reusing way-A's degrading client for a cache write). The one hard-to-reverse call — publish-from-refresh-only — is recorded as docs/adr/0001-movieupserted-published-from-incremental-refresh-only.md.

  • Q1 · What is the event? → A: MovieUpserted — the publisher's truth ("Catalog wrote this row"), noise absorbed by the idempotent consumer (not a narrower MovieTitleChanged).
  • Q2 · When does it publish? → Incremental-refresh path only (CatalogUpserter.refreshMovies), never backfill (upsertPage) — ADR 0001. The stream = "changed while Booking was live"; the read model is seeded by lazy backfill, not by replaying the catalogue.
  • 4A · Publish reliability? → Direct publish now, AFTER_COMMIT (via @TransactionalEventListener so a rolled-back refresh never announces a phantom). Broker-down = lost event, self-heals via lazy backfill, fully fixed by M4's outbox. Named, not hidden.
  • 4B / Q3a · Consumer idempotency + ordering? → UPSERT keyed by movie id (naturally idempotent — no processed_events yet) + an updatedAt guard that drops an event whose timestamp ≤ the stored one.
  • Q3b · eventId on the wire? → Now, but intentionally unused until Phase 4 (forward-compatible for the processed_events dedupe; documented as carried-not-consumed so it's not mistaken for a broken dedup).
  • Q3c · What is updatedAt? → Catalog's Movie.@LastModifiedDate (per-row monotonic, single clock). NOT a publish-time stamp — that would defeat the guard under the exact redelivery it defends.
  • 4C · Cold-start seeding? → Lazy backfill on miss — this is what makes way B non-empty in a fresh demo (given Q2). Consequence, stated: way B is network-free only for already-cached movies.
  • Q4a · Which Catalog call for backfill? → A new CatalogClient.titleById with throw-on-unavailable / empty-on-404. NOT titlesByIds — its silent degrade would poison the persistent cache (a null on an outage hides the miss and suppresses the retry).
  • Endpoint shape: → ?source=composition|readmodel on the existing /bookings/my (default composition); unknown value → BOOKING_VALIDATION_ERROR. Not /v2 (no contract change), not a config flag (2.4 needs both live at once).
  • Broker test: → Hermetic direct-invoke of the projector (idempotency, guard, lazy-backfill). The exchange/queue/binding/routing-key/converter wiring is not covered by these — that seam is verified once, manually, in the 2.4 live demo. Stated, not pretended.
  • New concept file? → Yes — docs/concepts/cqrs-read-model.md, linked from concepts/README.md.
