Plan: OpenAPI / Swagger for the services

Date: 2026-07-05 Author: Claude Code + Mohamed Status: APPROVED — implementing
Milestone: cross-cutting (edge / BFF-adjacent) Service: catalog · booking · payment · gateway Schema §: all controller surfaces

1. Summary

What: add springdoc-openapi to the three services that have controllers (catalog, booking, payment) so each serves a live OpenAPI 3.1 spec + Swagger UI, then aggregate them behind one Swagger UI at the gateway (http://localhost:8080/swagger-ui.html) with a service dropdown. Why now: the API contract is currently being hand-authored as wire-level Markdown in docs/frontend/; springdoc introspects the controllers, record DTOs, and Bean-Validation annotations at runtime and serves an always-in-sync contract instead — so a frontend can be built against it without reading Java or the repo. Microservices lesson: each service knows only its bare paths (/movies), but the client sees one aggregated contract on /api/... through the gateway — reconciling per-service specs into a single client-facing contract is the edge/BFF cost we surface here.

2. Milestone & schema link

  • Field-guide milestone: none directly — OpenAPI is a new cross-cutting workstream (it applies to every service's controllers). Closest theory: the API gateway / BFF section (edge concerns).
  • Schema doc: touches every controller surface, no data-model change. The monolith (ARCHITECTURE_AND_SCHEMA.md) already used SpringDoc — this carries that prior art into the split.

4. Options

Docs topology — how the frontend reaches the specs. Depth and doc-conventions were also chosen (full contract on all three + concept file + roadmap update); those are folded into the recommended path below.

Recommended

Option A — Aggregate at the gateway

springdoc on each backend service; the gateway hosts one Swagger UI with a service dropdown.

  • One URL (:8080) matching how the frontend really calls the system.
  • Paths read as the public /api/... via per-service Server URLs.
  • Teaches the edge/BFF cost: many per-service specs → one client contract.
  • More setup: gateway routes for each /v3/api-docs + StripPrefix handling.

Best when: there's a real frontend consuming through the gateway. (Chosen.)

Option B — Per-service only

Each service exposes its own Swagger UI; no gateway work.

  • Simplest; nothing to aggregate.
  • Frontend dev juggles 3 URLs (:8081/:8082/:8083).
  • Shows bare paths (/movies), not the real /api/movies they must call.

Best when: internal, per-service debugging only.

Option C — Per-service + static bundle

Per-service springdoc plus a build step dumping each spec to a static file in docs/.

  • Offline, versioned specs the frontend can diff.
  • No live aggregated UI.
  • Extra Maven plugin + regeneration discipline.

Best when: contract-diffing in CI matters more than a browsable UI. (Deferred as a follow-up.)

6. Risks / microservices cost felt

Bleeding-edge version. springdoc 3.0.3 is built on spring-boot-starter-parent:4.0.5; we run 4.1.0 (same major, one minor ahead). Verified 3.0.3 exists on Maven Central and targets Boot 4. Residual risk is the minor bump — validated at build time on payment first before spreading. Fallbacks: static-spec only, or a different 3.x patch.

The /api prefix / distributed-docs cost. The client sees /api/movies (aggregated at the gateway); no single service knows that path — it only knows /movies. The per-service Server URL + gateway aggregation is the production way to reconcile isolated specs into one client-facing contract (BFF-adjacent).

Contract drift on code. springdoc can't see setProperty("code", …), so the @ApiResponse docs can drift from the real <Service>ErrorCode enum. Mitigated by documenting codes close to the enum and flagging the coupling in the concept file.
